# Jose phase 7 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish Jose (stop, cancel, a queue, every entry point through him, planning from the request) and close the agent phases' leftovers the owner folded in.

**Architecture:** Two new small modules in `src/services/jose/` (`joseStop.ts`, `joseQueue.ts`) used by the one pipeline (`runJoseCommandExecutionPipeline`); everything else is changes to existing files: the planner prompt, the request store's statuses, the board, Chat, Telegram, the content runner, the batch orchestrator, the skill pick, the help loop (hand-offs), `policy_gate.rs` and CI.

**Tech Stack:** TypeScript/React (Vitest), Rust (Tauri 2, `cargo test`), WebdriverIO desktop specs, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-27-jose-phase7-design.md`

## Global Constraints

- Plain answers in Chat never queue and never get slower.
- Reuse what exists: the request store, `adaptPlan()` and the help loop, `submitStepsToJose()`, effects and approvals, the project lock (`releaseProject()`), skill results (`skillStats()`), Telegram button tokens, `onOpenJoseBoard`.
- No hardcoded model names in the app; the CI model is set in the CI file only.
- Plain words on screen, no em dashes in new screen text; English only; Windows first.
- Docs change in the same commits as the code; new services and components get CLAUDE.md rows (`verify:dnd-coverage`).
- Keep LF/CRLF as each file already has it; never `git add -A`.
- Never print or commit a key; live checks use keys typed into Settings.

## Review Focus

1. Stop pressed while Marcus is sending: the send goes out exactly once and the request says it was sent, then stopped. Test in Task 2.
2. A queued request whose ahead-of-it request waits for your approval: the queued one runs; the waiting one rejoins at the back when carried on. Test in Task 4.
3. The app closes with two requests queued: at start both are queued again in their order, and nothing runs twice. Test in Task 4.
4. A hand-off asking for a send from a step that is itself a review: the added Marcus step still waits for approval, and a second ACTION line in the same step adds nothing. Test in Task 12.
5. `node ../other/x.js`, `node C:\x.js`, `node -e "…"`, `node --require y x.js`: all refused by the backend. Test in Task 13.
