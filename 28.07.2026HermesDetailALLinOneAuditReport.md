### Connector Policy Architecture

All 24 connectors are policy-gated through a two-layer system:
1. **Primary gate:** `policyEnforcementService.ts` — `evaluatePolicyGate()` — fail-closed on missing credentials, Zero-Cost Mode blocks paid connectors, per-agent allowlists/blocklists
2. **DSL layer:** `policyDslService.ts` — default-deny, `require_consent` for irreversible/costly actions, explicit allow for low-risk external actions

```
Connector Call → policyEnforcementService.evaluatePolicyGate()
  → fails if: credentials missing OR Zero-Cost Mode AND paid connector
  → then policyDslService.evaluateAction()
    → deny: blocked immediately
    → require_consent: needs user approval
    → allow: proceeds to invoke()
  → connectorOutbound.js dispatches via Tauri invoke()
```

11 of 156 connector files reference policy gating. The policy system is the core security model.

## 3. Security Audit (Deep)

### 3A. Rust Backend Security

#### Command Injection — CRITICAL

**File:** `src-tauri/src/lib.rs`, ~1537-1540

```rust
let script = format!("printf '%s' '{}' | base64 -d > '{}'", raw, path_str);
Command::new("sh")
    .args(["-c", &script])
    .output()
```

**Issue:** `path_str` is derived from user-controlled `folder` and `filename` parameters. Neither is sanitized for shell metacharacters. A single quote (`'`) in the filename breaks out of the shell-quoted string, allowing arbitrary command execution.

**Proof of Concept:** `filename = "test'; rm -rf /; '.png"` would execute `rm -rf /` after the base64 decode.

**Note:** The Windows PowerShell path (lines 1518-1527) is safe because it uses a .NET method call with proper single-quote escaping, and `raw` is base64-only characters.

**Fix:** Replace shell invocation with a pure Rust base64 decoder (e.g., `base64` crate) and `std::fs::write()`. Do not construct shell commands with user-controlled paths.

---

#### Arbitrary Executable Execution — MEDIUM

**File:** `src-tauri/src/lib.rs`, ~1478-1481

```rust
Command::new(&py)
    .arg("main.py")
    .current_dir(&dir)
    .spawn()
```

**Issue:** `py` is derived from user-controlled `python_exe` parameter. Unlike `execute_command_verified` (line 443), this function does **not** call `allowed_program()` to validate the executable. An attacker who can influence the frontend (e.g., via XSS, compromised settings, or malicious plugin) can set `python_exe` to any executable and have it spawned.

**Fix:** Add `allowed_program(&py)` validation before spawning, consistent with `execute_command_verified`.

#### Safe Patterns (Verified)
- `execute_command_verified` (lib.rs:436) — validates `program` via `allowed_program()`
- `plugin_runtime.rs` (line 464) — validates `tool.program` via `allowed_program()`
- `runtime_manager.rs` — uses `resolve_exe()` which returns known paths from a whitelist
- `open_url` (lib.rs:1190) — validates URL starts with `http://` or `https://`

### 3B. Policy Gate System — Rating: A (Best-in-Class)

#### Policy Enforcement (`policyEnforcementService.ts`)
- **Fail-closed on missing credentials:** If a connector's required credentials are not configured, the gate blocks the call and writes an audit receipt
- **Zero-Cost Mode:** Blocks all paid connectors unless explicitly overridden
- **Per-agent allowlists/blocklists:** Each agent has an explicit list of allowed action prefixes
- **Approval gating:** Irreversible/costly actions require explicit user approval

#### Policy DSL (`policyDslService.ts`)
- **Default deny:** Unmatched actions are denied
- **require_consent:** Irreversible/costly actions (financial, external publish, agent spawn) require explicit consent
- **allow:** Read-only and internal memory operations allowed by default
- **deny_credential_export:** Block exporting credentials or secrets
- **deny_delete_all:** Block bulk delete operations

#### Policy Rules (`policy.yaml`)
7 explicit rules covering: delete-all blocking, consent for external publish, consent for financial actions, read-only allow, internal memory write allow, credential export deny, agent spawn require_consent, connector publish require_consent, connector paid require_consent, and a low-risk external catch-all.

### 3C. Frontend Security

#### XSS — No Issues Found
- No `innerHTML =`, `document.write(`, or `dangerouslySetInnerHTML` patterns in production code
- All `JSON.parse` calls operate on trusted or size-limited inputs:
  - localStorage data (same-origin)
  - Verified WhatsApp webhook body (after HMAC signature verification)
  - Ollama streaming response lines

#### localStorage Credential Storage — MEDIUM (2 issues)

**Issue 1:** `connectorAuth.js` lines 25, 40, 84 — connector credentials fallback to localStorage. The design intent is to use Tauri KV (SQLite), but `writeAllCredentials` falls back to `localStorage.setItem` if `invoke('kv_set')` throws synchronously. `readAllCredentials` reads from localStorage on every cold start. Credentials (API keys, tokens, secrets) are accessible to any XSS payload.

**Issue 2:** `OnboardingWizard.tsx` line 508 — Telegram bot token stored directly in `localStorage.setItem('alphonso_telegram_bot_token_v1', token.trim())`. No encryption, no migration to KV store.

**Fix:** Remove localStorage fallback for credentials. Use Tauri KV store exclusively. Migrate Telegram bot token to KV store.
